# Plugin descriptor

`phoenix-plugin.json` describes a separately installed connector plugin (ARCHITECTURE.md section 3.15). `phoenix_plugin` is the plugin-interface major version it implements. It declares the connector name, how to recognize the connector (MCP server names, hosts, CLI commands), its declared tier (a ceiling, never proof) and the operations it covers, its read-only and volatile operations, versioned key rules that remove argument paths from call keys, an optional entity map per tool (kind, entity type, id and item paths, how a list shows it is complete, and equality or range filters), and up to two commands: `capture` (the sidecar) and `serve` (an emulator at `http` or `tool` level). Both speak newline-delimited JSON on stdio or plain HTTP.

## Process protocol, major version 1

The host discovers descriptors in explicitly supplied package directories or install roots (including scoped packages). It validates the descriptor before launching anything. Command arrays are executed without a shell. Capture commands run beside the harness; serve commands always run through `Sandbox`, with only explicitly supplied environment values and mounts. A replay caller mounts the installed plugin and Snapshot and sets the container working directory to the plugin's path. Paths in initialization are container paths for replay processes.

Requests are JSON objects with `phoenix_plugin: 1`, an integer `id`, `method` and a `params` object. Replies repeat the version and id and contain exactly one outcome:

- `status: answer` with `value` (including an explicit `null` for a successful empty result).
- `status: unsupported` with `reason`, meaning the operation missed and the answer chain continues.
- `status: invalid-input` with `reason`, meaning the input cannot be used.
- `status: execution-failure` with `reason`, meaning execution failed, never an empty success.

The host first sends `initialize` with optional `snapshot`, `seed`, `now` (the engine's clock endpoint), `segments` (capture segment paths), and `read_only` (the descriptor's declared read-only operation names). The plugin replies `answer` when ready. `call` takes `op` and `args`; in capture mode the host refuses a `call` not in `read_only`. `state` asks for emulator state for `end_state`. `capture` takes the sidecar's capture request. The connector-specific input and answer stay opaque to the host.

A capture target is an MCP server command, an HTTP URL, or a command-line tool (`cli`). The `plan` request names the target's `surface`, and the plugin plans reads for that surface only. For a command-line tool, each planned read has the command's name as `op` and `{argv, stdin?}` as `args`, with `argv[0]` equal to `op`. The host runs the target command with the rest of argv, without a shell, and writes `stdin` (a string) to it. A read is allowed only when a `read_only` entry, split on spaces, matches the first words of argv, so `"tool list"` allows `tool list --all` but not `tool send`. A replay uses the same rule to decide whether a CLI call is a read. The observation's request is the CLI invocation and its response is the frame list, the same shape as a recorded CLI call. Frame bytes are scanned for secrets like any other body. Capture orchestration and coverage belong to the capture caller, not this protocol transport.

For `stdio`, each request and reply occupies one newline-terminated line on stdin/stdout. Requests may overlap and replies are matched by id. Diagnostics go to stderr. For `http`, the launched process prints one readiness line on stdout: `{"phoenix_plugin":1,"ready":{"url":"http://127.0.0.1:9000/plugin"}}`. The host POSTs one request to that loopback URL and expects HTTP 200 with one reply JSON object. Redirects are not followed. Inside a replay, HTTP requests travel through the private relay channel to the plugin's loopback listener, never through a published container port.

Unknown versions, malformed replies, a closed protocol stream, and process death are host errors. A pending request fails instead of substituting an answer or an empty world. Calls have a host-real-time timeout (30 seconds by default); the host never retries an operation. The runner owns interrupt/resume decisions.

## Emulator serving and comparison

`startServingPlugin` is the replay-serving adapter. Initialization supplies `snapshot` and `seed` as container paths, and `now: file:///phoenix-clock`. That read-only clock endpoint is updated from the engine's virtual clock before each request; libfaketime drives the process clock. Each `call` and `state` also carries `now` as an ISO timestamp. Calls on one plugin are serialized. No outbound connection is forwarded, including connections to the engine relay; local HTTP protocol requests still use the private channel. Mount only the plugin, its Snapshot/seed and its clock, with no production credentials.

A serving `call` carries `surface`, `layer`, `op`, `args`, and `raw: {body, head?}`. `body` is a canonical base64 string of the request bytes; `head` is the HTTP request head when applicable. An `answer` value is `{body, head?}` with the response body in base64. HTTP heads contain `status`, optional `statusMessage`, and an alternating name/value `headers` array. HTTP plugins return identity-encoded bodies and matching headers. MCP bodies are complete JSON-RPC responses with the request's id. A `tool` plugin covers MCP or CLI calls; an `http` plugin covers vendor-API calls. When a CLI call's stdin is not a terminal, `raw.stdin` holds the piped bytes in base64. The host waits for stdin to end before it sends such a call to a plugin. It waits only when a plugin answers or mirrors the call, so a replay with no plugin for that connector never waits. An answer's frames need not repeat the input. Operations not in the descriptor are unsupported, never guessed. State replies remain connector-specific JSON.

When a replay resumes a harness's own session, a plugin serves every connector the session used whose name is the plugin's `connector` or one of its `recognize.mcp_servers`. Its snapshot is the session's answers for that connector up to the cut, plus the reads after the cut that come before the session's next write. It is a capture segment: one JSON line per call and per result, with `kind`, `connector` (the plugin's), `surface`, `op` and `body.inline` holding the JSON-RPC message. A Snapshot named in the Workbench settings replaces it.

The answer chain mirrors calls answered by earlier resolvers into the emulator. A differing response is reported while the recording remains authoritative. An unsupported read is a miss; an unsupported mirrored write stops the sample because the emulator's state could no longer be trusted. Invalid input, execution failure and malformed answers are errors, never fallback answers.

`plugin-kit` accepts ordered recorded exchanges (request/response bytes, normalized operation/arguments, observation time and optional intervening messages) and an optional expected end state. It starts a fresh sandboxed plugin, compares exact response bytes and HTTP heads, also reports JSON-field differences, reports unsupported/intervening protocol behavior, and queries final state. It never normalizes away timestamps, ids, recurrence or attendee fields. Without an expected end state it returns the actual state but cannot claim end-state equivalence.
## Entity map paths

Operation names use the answer chain's names (for example, `tools/call:get_event`). Paths are JSON Pointers; the empty string means the root. `id_path` addresses an id in the normalized arguments and in each entity. `items_path` addresses the entity or entity array in the response payload. MCP payloads are `structuredContent` or the JSON in a single text content block; HTTP payloads are JSON bodies. Unsupported envelopes miss rather than being guessed.

`complete` is a pointer to a boolean `true`, or `unpaginated` for an explicitly unpaginated list. Only an unfiltered observation establishes completeness of the whole entity collection. Filtered lists still contribute known entities. Equality filters compare JSON values exactly. Range arguments are inclusive `[minimum, maximum]` pairs of numbers or strings, compared in their native order. Other arguments miss. A known-complete collection can answer a missing get with a null payload; an unseen id in an incomplete collection misses.

Writes are not invented by the overlay. A served write's returned entity updates it; a successful delete removes the id. A write with no known returned entity (including an error or a synthesized acknowledgement) leaves its target unknown. An unmapped write invalidates the known collection. A connector owned by an emulator has no overlay state.

## Capture orchestration

`capturePlugin` is an explicit per-connector opt-in. It starts the capture command with only that connector's segment paths. The command reads those files, then answers `capture` with `phase: plan` with `{ "calls": [{ "op": "tools/call:get_event", "args": { "id": "…" } }] }`. The host rejects the entire plan before opening an upstream connection if any operation is absent from the descriptor's `read_only` list. An annotation is not authorization.

The host opens its own stdio MCP process, or makes its own direct HTTP requests to the explicitly supplied target. It never accepts an agent connection. After recording the timestamped, secret-stripped results, it sends `capture` with `phase: complete` and `results` containing each operation, its arguments and its recorded request/response observation. The command returns `{ "collections": [{ "entity": "…", "complete": false }] }`. The host adds its observed time span and writes coverage. A failed sidecar writes incomplete coverage and never changes an agent reply. The launcher's optional `plugins` array runs these sidecars after the agent and collector stop; by default it runs none.

Each `prefetch` event's JSON body contains `op`, normalized `args`, `request` and `response`. Message bodies are secret-stripped before serialization. They are UTF-8 strings, or base64 strings with `body_encoding: base64` for non-UTF-8 bytes; unreadable bodies retain the trace's `unscanned` flag. HTTP messages also have their protocol heads. The event's own position and timestamp identify the observation, and the answer index attaches the recorded writes completed before that position. Prefetch is separate from the session's own answers.
