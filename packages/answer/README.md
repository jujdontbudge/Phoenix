# Answer

## Emulators

`Emulators.start(configs, () => clock.now(), onDifference?)` creates independent plugin processes. Each config is `{plugin, options}`, where `options` is plugin-host's `ServingOptions`: a sandbox, explicit mounts, a private clock file, and container-local Snapshot/seed paths. Give each sample and connector its own clock file and sandbox. Pass the world as the third argument of `replayCtx`; the registered emulator resolver follows recorded answers (and the overlay when installed).

`answerCall` mirrors earlier answers into the emulator so recorded writes do not leave its world stale. A caller that serves an answer outside `answerCall` must also `await world.observe(call, answer, exchange.observedAt)` first. The engine does this automatically when given `emulators`; it writes differences as `fidelity.emulator_differences` trace events and exposes `engine.state(connector)` for end-state checks. Unsupported mirrored writes and plugin failures stop the sample. `skip_resolvers: [emulator]` disables both serving and mirroring in the engine. Always close the world; `engine.close()` does so.

The replay answer chain over one run's evidence. `buildIndex` turns trace events (run order, from a capture view or a bundle's run evidence) into exchanges, each with its call key, read-only flag from the locked classification, and write history. Every exchange is part of the continuation: a moment made from a capture replays from the beginning. `replayCtx` holds one sample's state: the write history per connector and the exchanges already served.

`answerCall` runs the resolvers in `resolvers/index.ts`, in that order, skipping any a manifest removes for the connector, and returns the first answer. When every resolver misses it returns a divergence with each resolver's reason; it never falls back to a live connector. Each resolver is its own module, so a later resolver is one file and one line in that list. The recorded resolver serves a current exchange from the continuation with the same key byte for byte, the k-th call gets the k-th answer, and a read-only, non-volatile call past the recorded count gets the last current observation as `derived` ("repeat of last observation") unless `repeat_reads: false`. An exchange is current only while its stored write history equals the sample's, so a recording never answers for a world the candidate changed or a write it skipped.

## Simulator

Pass an optional fourth argument to `replayCtx` (after the emulator world): `{ moment, provider, improverModel, store: new SimulatorStore(sharedRoot), clock }`. `startEngine` accepts the same `simulator` options without `clock`; it uses the recorded start-point epoch as the stable clock context, not wall-clock inference latency. Use one shared store for the moment's baseline and all samples. A different moment, call key, write history, clock context, provider configuration or response schema gets a separate entry. Publication is durable and atomic with a hard link: concurrent writers and a restarted process read the first published answer, never a partial file.

The registered simulator runs after earlier resolvers and only with `allow_synthesized: true`. MCP tool results are checked against the protocol content envelope, the format inferred by `wire` from that operation's recorded results, and any `outputSchema` from recorded `tools/list` (against `structuredContent`). The local `schemas/mcp-result-*.json` files contain only `CallToolResult` and its transitive definitions from the official [2025-11-25](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-11-25/schema.json) and [2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.json) schemas, with descriptions removed. Request metadata or the recorded negotiation selects the era; the new era permits any JSON structured content. HTTP responses use an inferred status/body format; explicit schemas can be supplied by connector/op in `outputSchemas` and apply to the HTTP body or MCP `structuredContent`. Without a declared schema or an observed format these surfaces miss, rather than inventing an unchecked format. Invalid JSON or schema violations retry up to three times, then diverge; stored answers are revalidated too. MCP protocol/lifecycle methods are not synthesized.

CLI synthesis uses the known invocation protocol even without a recorded answer for that operation. The simulator's LLM returns `{stdout: string, stderr: string, exit: {code: number|null, signal: string|null}}`; exactly one exit code (0–255) or nonempty signal is required. An optional CLI `outputSchemas[connector][op]` checks that whole value. Recorded stdout/stderr and exit status supply observations, not extra format restrictions. After validation and write-once storage, UTF-8 stdout/stderr and a JSON exit control become three base64 `back` frames in the responder's frame-array format. No executable is launched, no input interaction is invented, and write calls remain no-ops.

All answers are tagged `synthesized`, so the engine's existing trace provenance feeds checks' forward taint and discount rules. Non-read-only calls produce only a no-op acknowledgement: no overlay, emulator, end-state evidence or live connector is touched. The sample still records the attempted write in its write history, as it does for every served non-read-only call. Simulator configuration requires a different LLM id from the Improver (ignoring a provider prefix); the stateless provider request receives only the call, response formats and recorded tool observations, never the Improver's prompt or conversation.
## Overlay and prefetch

The registry also includes `overlay` and `prefetch`. Supply a descriptor's `entity_map` in the connector policy (or `entityMaps` to the engine). Each replay context owns its overlay state; it is seeded from answers the session already holds before the cut (marked `frozen` in the index; only the resume path's stand-in has them) and current capture-time observations, never continuation entities the candidate hasn't observed. All served answers are observed so replay writes update the overlay using their returned entities, and unknown effects invalidate their targets. Gets derive from known entities and lists require a complete collection with only declared simple filters. Recorded/prefetched gets can remain current across unrelated mapped writes. Lists conservatively become stale when writes could change membership. See `spec/plugin.md` for path and capture-event conventions.

`prefetch` serves only declared non-volatile read-only operations, with recorded provenance and the same currency check as run evidence. It never runs a live read during replay. The overlay is bypassed when an emulator owns the connector, so the two never hold competing state.

## Recorded layout read here

- **MCP**: one event per JSON-RPC message on the connection's stream, `call` for harness-to-server and `result` for server-to-harness, body as received. Requests pair with responses by id. Server messages while a request is open belong to it and are replayed before its result; a harness reply to a server request is compared with the recorded one. Non-`tools/call` methods are protocol traffic and never enter a write history.
- **HTTP**: one stream per exchange: `meta` (request head JSON), `call` (request body), `meta` (response head JSON), `result` (response body). The op is `METHOD host/path`; arguments are the query string and the decoded body.
- **Tap captures**: the collector's `meta/open` wrapper contains `{ surface, connector, meta }`. HTTP heads and bodies use `frame:back:1`, `frame:out:0` and `frame:back:2`; empty bodies may be metadata frames. Both this layout and the engine's flat-head layout are indexed.
- **CLI**: one stream per invocation, with its invocation in `meta/open` or the engine's agent-level `call`. `frame:<out|back>:<0|1|2|3>` bodies hold stdin, stdout, stderr or a control. Chunk offsets and monotonic timestamps reconstruct the interaction order; the exit control completes the exchange. Engine `fragment:*` records carry individual frames. The key uses the full invocation object, the operation is `argv[0]`, and the recorded answer is a JSON array of `{ dir, stream, bytes: base64, last }` frames. Low-level input frames in sample traces are `layer: under`, leaving exactly one agent action per invocation.
- **MCP Streamable HTTP**: the operation and arguments come from the JSON-RPC message, not the HTTP path or ephemeral request ID. Protocol/session/cursor headers participate in matching. GET, DELETE, empty bodies and server-request replies are recorded lifecycle exchanges, not synthetic successes. Recorded SSE blocks retain their bytes and carry request-ID dependencies reconstructed from chunk timing; the engine uses those dependencies to preserve cross-request interactions and the position of notifications. The response head and decoded content encoding stay with the exchange.

Normalized MCP arguments are `params.arguments` for `tools/call` and `params` without `_meta` otherwise. The core removes no other argument path.
